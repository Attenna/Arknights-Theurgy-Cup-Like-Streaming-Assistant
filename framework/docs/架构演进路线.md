# 架构演进路线（协作契约与解耦强化）

> 核心原则：**边界靠目录和 CI 守，协作靠事件和契约走，升级靠真实痛点触发。**
> 本文档是模组协作机制的目标态规范与演进计划；AGENTS.md 只保留短平快执行规则，
> 细则一律指向本文。落地任务在 GitHub Issues 跟踪（标签 `architecture`）：
> **#1** EventCatalog+订阅owner · **#2** PluginContext访问层 · **#3** CI禁令 ·
> **#4** DataKeys+schema_version · **#5** payload校验+契约测试 · **#6** 协作集成测试 ·
> **#7** 插件模板脚手架 · **#8** 最小化ServiceRegistry（按需）

## 1. 三条铁律（全局强制）

### 铁律 1：插件不引用插件
- 严格禁止在插件代码中 `preload` / `load` **其它插件**的脚本文件；
- 严格禁止通过 `get_node` 跨插件访问节点（含 `../xxx` 相对路径形式）；
- 插件间协作**只允许**以下官方通道：
  1. `EventBus` 事件（广播 / 通知）
  2. `plugin.json provides` 能力声明（经内核中介）
  3. `DataService` 共享数据（禁止传递节点引用）
  4. `PanelHost / mount_panel` 面板挂载协议（现名组 `control_panel_base` + mount 约定，落地时更名）

### 铁律 2：服务只从 PluginContext / Kernel.get_service() 获取
- 禁止在插件代码中硬编码全局路径 `/root/Kernel` 直接访问内核实例；
- 核心服务层不得持有任何具体插件的引用或依赖；
- Kernel 仅负责组件装配与生命周期管理，不含任何业务逻辑。
- ✅ **PluginContext 访问层已落地**（ADR-0001 / issue #2）：`Plugin` 派生经基类 getter
  或 `self.context` 取服务，非 Plugin 派生脚本经 `PluginContext.for_node(self)`；
  `mods/`、`core/` 硬编码已清零，CI 禁令全量生效（`src/` 引导壳白名单）。

### 铁律 3：事件名 / 数据字段名必须全局常量化
- 统一创建 `EventCatalog.gd`（事件目录）与 `DataKeys.gd`（数据键常量）；
- 禁止裸字符串事件名（如 `"match_stage_changed"` 直接写进 emit/connect）；
- 新增事件必须同步登记目录并完整编写 payload 字段说明（必填 / 可选 / 类型）；
- debug 构建自动做 payload 合法性校验，release 关闭校验保证性能。
- ✅ **EventCatalog.gd 已落地**（autoload）：事件名常量 + payload 契约注释；
  `emit_event` 在 debug 构建校验事件名已登记，release 跳过。
- ✅ **DataKeys.gd 已落地**（class_name，issue #4）：全部共享数据字段常量；
  `DataSchema` 提供字段类型 / 必填定义、加载校验（告警不阻断）与版本迁移；
  契约本体见 README「数据规范」，契约测试随 issue #5 测试框架落地。
- ✅ **payload debug 校验已落地**（issue #5，ADR-0003）：EventCatalog `PAYLOAD_SCHEMAS`
  机器可读契约；`emit_event` debug 构建校验 payload（问题告警含事件名与字段，不阻断分发）；
  契约测试位于 `tests/`（轻量 runner，真实无头启动 `res://tests/test_main.tscn`）。

## 2. 新增功能时的决策顺序（从上到下，禁止跳级）

| 需求 | 手段 |
|------|------|
| 通知其它模块状态变更 | `EventBus` 发布事件 |
| 声明自身可提供的能力 | `plugin.json provides` 声明 |
| 查询其它模块已注册能力 | `PluginRegistry` 只读查询 |
| 挂载子面板 | `PanelHost / mount_panel` 约定 |
| 跨插件共享数据 | `DataService`（禁止传节点引用） |

**同步取返回值**（如需引入最小化 `ServiceRegistry`）必须三项全为「是」：
1. 该逻辑天然属于核心服务范畴，无法由单个插件实现？
2. 无法用「事件发布 + 状态轮询查询」替代？
3. 已在 ≥3 处重复实现 / 存在多版本兼容需求 / 出现过多次实现不一致？

## 3. 事件设计规范

- 命名：`领域_动作`，过去式后缀表示已发生（`match_stage_changed` / `score_updated`）；
- payload 为 Dictionary，但必须有明确契约：必填 / 可选字段与类型写入 EventCatalog 注释；
- **禁止把 EventBus 当 RPC**：请求/响应优先走核心服务；确需事件实现的必须携带
  `request_id` + 一次性回复事件 + 超时时间；
- 订阅绑定 owner：`subscribe(name, cb, owner)` 签名，插件卸载时自动
  `unsubscribe_all(owner)`，保证热重载无悬空订阅；
- 高频事件必须节流 / 批量合并，禁止每帧无差别广播。

## 4. 数据契约规范

- `DataService` 加载契约数据时自动执行 schema 校验（问题告警不阻断，优雅降级）；
- 共享数据携带 `schema_version` 信封，字段变更必须编写迁移函数并递增版本；
- README 的 JSON 规范即正式契约本体，配套 `data_schema.gd` 定义、示例数据、契约测试；
- 字段名统一从 `DataKeys` 引用，禁止插件侧硬编码字段名。
- ✅ **已落地**（issue #4）：`core/data_keys.gd`（字段常量）+ `core/data_schema.gd`
  （类型 / 必填定义、`validate_item` 校验、`migrate` 版本迁移）；
  DataService 读取链路接入校验；存量插件裸字段名已迁移为常量。
  契约测试（players.json / teams.json 示例）随 issue #5 测试框架统一落地。

## 5. 核心服务演进规则

- 新增核心服务必须先写 ADR（`framework/docs/adr/NNNN-标题.md`）：为何插件做不了、
  生命周期定义、异常失败模式；
- 服务间用构造注入，禁止互相 `get_node` 获取实例；
- 保持 PluginManager「依赖解析失败自动回滚、先构建后替换」机制不变；
- `PluginRegistry` 对外只返回只读快照，禁止外部修改注册表实例。

**若引入 ServiceRegistry，仅最小化三接口**（触发条件见第 2 节）：
`register_service(name, impl, version)` / `get_service(name, min_version)` / `unregister_service(name)`；
接口名常量化，仅核心与受信插件可注册。

## 6. 工程习惯与 CI 门禁

- CI 强制 grep 禁令（命中即阻断合并）：
  1. 禁硬编码 `/root/Kernel`（白名单：`src/` 引导壳；`core/`、`mods/` 均已清零）；
  2. 禁插件目录内 `preload/load` 其它插件脚本；
  3. 禁跨插件路径形式 `get_node("../xxx")`；
- 测试覆盖：事件名与 payload 契约测试；两插件仅事件协作的集成测试；
  热重载时订阅清理测试；
- 日志统一携带 `plugin_id`、`event_name` 上下文字段；
- 维护插件模板脚手架（`plugin-template/`），从源头减少复制粘贴错误；
- AGENTS.md 只记短平快规则；**ADR 专门记录「当前暂不引入某机制」的决策原因**。

## 7. 三阶段路线

| 阶段 | 内容 | 现状 gap | Issues 标签 |
|------|------|----------|-------------|
| **1 薄护栏** | EventCatalog + 订阅 owner 清理 + PluginContext 访问层 + CI grep 禁令 | 全部落地：#1 EventCatalog/订阅 owner、#2 PluginContext、#3 CI 禁令 | `phase-1` |

## 8. 明确永久不做

- ❌ RPC 机制、事件 schema 代码生成
- ❌ 全量 DI 容器、为"类型安全"而做的无收益架构重构
- ❌ 跨插件节点引用
- ❌ 事件总线承载大数据流（走 DataService）

> **最终准则**：让协作靠事件和目录边界约束，让升级靠真实业务痛点触发，
> 绝不让未来的短期偷懒变成长期架构债。
