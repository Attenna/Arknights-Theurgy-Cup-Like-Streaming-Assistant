# 代码库导览

> 面向第一次阅读本仓库的人。目标：2–3 小时建立完整的心智模型（见文末「从哪里开始阅读」）。
> 配套文档：[AGENTS.md](../../AGENTS.md)（协作规范）、[STRUCTURE.md](../../STRUCTURE.md)（目录参考）、
> [插件开发指南](插件开发指南.md)（契约细节）。

## 一、它是什么

Godot 4.5.1（Mono）直播间助手：一个 1920×1080、不可缩放、背景透明的窗口，渲染可切换的直播场景
（比赛场、主视觉），外加一个控制面板窗口，用来管理选手 / 队伍 / 解说并切换场景。

规模不大：核心约 1,770 行 GDScript，`mods/` 约 3,100 行，契约测试约 370 行。
但边界规则很明确——**理解规则比读实现更重要**。

## 二、一个核心理念

本仓库不是「带插件功能的应用」，而是「插件内核 + 第一个消费它的直播应用」。

```
开发仓库                                     部署目录
core/ + src/  ──导出──▶  演播室2.exe + .pck   ← 纯核心，mods 永不进 pck
mods/<id>/    ──拷贝/解压──▶  {exe}/mods/<id>/  ← 文件夹即安装
```

三个直接推论：

- `PluginManager` 里没有任何具体插件 id；
- 清空 `mods/` 后核心仍能启动（空窗口 + 降级日志），这是设计行为；
- CI 会 grep `core/`，一旦出现具体插件 id 就失败。

> 以 `_` 为前缀的目录（`_template`、`_test_pair_a/b`）在打包时被排除：`export_mods.ps1` 与
> `export_mods.sh` 按 `_*` 前缀判断，不需要在脚本里逐个登记名字。

组装发生在运行时，不发生在构建时。

## 三、先读这个：mod 是遗留命名

仓库里 "mod" 是 2.0 之前的遗留命名。`ModLoader`、`ModInterface`、`ModScene`、`mod.json`、
`mod_scenes` 组、`streaming_scenes` 清单键都是兼容层。"Plugin" 才是规范术语。
看到 `mods/` 目录时，心里翻译成 `plugins/`。

**唯一的承重规则：插件的能力只能通过 `plugin.json` 到达内核。** 没有 `preload`、没有节点跳转、
没有 `/root/Kernel` 查找。CI 的三条 grep 禁令、`get_panels_by_slot`、`PluginContext.for_node`
全都是围绕这一条规则的执行手段或人体工学包装。

## 四、启动顺序

1. **自动加载**（`project.godot`，顺序固定）：`EventCatalog`（事件常量与 payload schema）→
   `AppData`（exe 目录、用户目录、首次运行播种 `userdata/`）→ `Kernel` →
   `ModLoader`（遗留门面，只转发 `Kernel`）。
2. **`Kernel._ready()`**：把自己加入 `kernel` 组，创建 `EventBus` / `DataService` /
   `SceneDirector` / `PluginRegistry` / `FileWatcher` 五个子节点，把数据与场景服务接到事件总线，
   然后 `PluginManager.setup()`。内核没有业务逻辑。
3. **`PluginManager` 两阶段加载**：先扫描全部清单，再做依赖解析（Kahn 拓扑排序，
   `load_priority` 平局决胜），最后按序加载。缺依赖、依赖被阻塞、环形依赖的插件完全不加载——
   没有半加载状态。
4. **逐个插件**：实例化 `plugin.gd` → 注入 `PluginContext` → `on_load()` →
   把 `provides.scenes` 注册进 `SceneDirector`、`provides.panels` 注册进 `PluginRegistry` →
   登记热重载监听路径 → `on_enable()`。
5. **引导壳**：`src/scenes/main/main.tscn` 向注册表要 `slot="main_window"` 的面板，
   实例化控制面板窗口；开发调试可用 `--scene <id>` 直接进入某个场景（dev only）。

## 五、内核服务

| 服务 | 职责 | 文件 |
|---|---|---|
| `EventBus` | 类型化信号 + 通用 `emit_event`；按 owner 订阅，卸载时 `unsubscribe_all(owner)` 批量清理——热重载不残留订阅 | `core/services/event_bus.gd` |
| `DataService` | `userdata` JSON 读写，读取时做 `schema_version` 迁移与逐条校验（只告警不阻断） | `core/services/data_service.gd` |
| `SceneDirector` | `scene_id` → `PackedScene` 注册表；**先构建后替换**，直播画面不会黑屏；`rebuild_current()` 供热重载 | `core/services/scene_director.gd` |
| `PluginRegistry` | 能力索引；`get_panels_by_slot(slot)` 让 UI 找 UI 而不必认识插件 id | `core/services/plugin_registry.gd` |
| `FileWatcher` | 500 ms 轮询（Godot 没有 OS 级文件监听）→ 去抖 → 触发重载 | `core/services/file_watcher.gd` |
| `PluginManager` | 670 行的中枢：发现、依赖图、能力注册、级联重载与回滚 | `core/plugin_manager.gd` |

### PluginManager 内部地图

`core/plugin_manager.gd` 有 670 行，内部大致分四段：

1. **清单扫描与校验**：`_scan_manifests` / `_read_manifest` / `_normalize_provides`；
2. **依赖图**：`_resolve_load_order`，Kahn 排序 + `load_priority` 平局决胜，产出加载序与阻塞名单；
3. **能力注册与注销**：`_register_scenes` / `_register_provides` / `_register_watch_paths`；
4. **级联重载与回滚**：`_reload_single`（备份旧注册 → 注销 → 卸载 → 重新加载 → 失败回滚）、
   `reload_all`、`_try_load_blocked`。

读的时候按这个顺序跳。

## 六、插件契约

- 能力声明只走 `plugin.json`，不通过代码引用（见上文「唯一的承重规则」）。
- `plugin.json`：`id`、`api_version`、`dependencies`、`load_priority`、`hot_reload`、`watch`、
  `provides.{scenes,panels}`。
- `plugin.gd` 继承 `Plugin`，生命周期钩子 `on_load / on_enable / on_disable /
  on_before_reload / on_after_reload / on_unload`。服务从基类 getter 或 `self.context` 取；
  非 `Plugin` 脚本（面板、场景根节点）用 `PluginContext.for_node(self)`。
- 直播场景继承 `PluginScene`（`core/plugin_scene.gd`），由 `SceneDirector` 注入身份，
  并提供选手 / 解说数据访问。
- 面板分两级：`control_panel_base` 持有窗口并暴露 `mount_panel(id, packed)`；
  二级面板声明 `slot: "control_panel"`，在 `on_enable` 挂载、`on_disable` 卸载。

热重载（F5 或文件监听自动触发）会原位重建当前场景；新版本加载失败时回滚到旧注册，
不会把画面弄丢。

## 七、当前插件

| 插件 | 角色 |
|---|---|
| `streaming_arena` | 参考直播场景：180 秒倒计时与三颗连麦星、开局藏品 / 分队 / 干员、左侧 ID 栏。自带 24 MB 字体、纹理、着色器——新场景照它抄。 |

| `scene_manager_panel` | 列出 `SceneDirector.get_scenes_by_type("live")`，点击切换。 |
| `player_database` | 重量级插件：SQLite（自带 godot-sqlite GDExtension）、1,100 行服务、760 行面板、CSV 导入导出。SQLite 是权威库，导出契约 JSON 供 `DataService` 读取。依赖 `control_panel_base`。 |
| `_template`、`_test_pair_a/b` | 插件脚手架与「纯 EventBus 协作」的集成测试夹具。 |

## 八、数据：三个根

三条路径互不重叠，值得早点记住：

- **JSON 契约**（`players.json`、`teams.json`、`current_*.json`）、SQLite 库与 CSV 都在
  `user://userdata/…`，经 `DataService` 访问。字段名在 `core/data_keys.gd`，
  类型 / 必填 / 迁移在 `core/data_schema.gd`，散文式契约见 README 的数据规范部分。
- **静态美术**（`data/operators/{星级}/头像_*.png`、`data/squads/`、`data/relics.json`）
  从 `{exe}/data/` 读取，经 `AppData.get_exe_dir()` 拼路径。
- **`content/`** 是仓库里那份 `data/` 的源副本，没有代码引用它。
- `icon_path` 字段是不透明绝对路径字符串，没有代码替你解析。

三者不共享根是刻意的：JSON 契约与 SQLite 是运行时用户数据（可写、随用户走），
静态美术是部署资源（只读、随 exe 走），`content/` 是仓库源副本（不参与运行）。
混在一起会导致「用户数据被导出覆盖」或「美术资源被误写」。

## 九、护栏

- `.github/workflows/ci.yml`：三条 grep 禁令（`mods/` 内 `res://mods|plugins` 的 preload；
  `../` 跨节点；`core/` 与 `mods/` 内的 `/root/Kernel`）、「内核不认识具体插件 id」检查、
  无头契约测试。
- `tests/`：轻量断言框架（ADR-0003），真实无头启动 `res://tests/test_main.tscn`，
  失败退出码 1。
- `framework/docs/adr/`：0001 访问层、0002 订阅 owner、0003 测试框架——解释了这些规则为什么存在。
- `framework/docs/架构演进路线.md`：目标态规范与决策顺序。

## 十、定位说明（容易踩的坑）

- `PluginManager` 仍会扫描 `res://plugins`。该目录已不存在，所以每次启动都会打印一行无害的
  `插件目录不存在，跳过`。
- 部分注释仍写着 `builtin_control_panel` / `builtin_streaming_arena`
  （`src/scripts/main/main.gd`、`mods/streaming_arena/scripts/arena_scene.gd`），是改名前的残留。
- `main_vision` 没有出现在 README / STRUCTURE 的插件清单里；CI 的插件 id 名单也还没有
  `main_vision` 与 `player_database`。
- `framework_cs/` 是休眠代码：没有 `.csproj`，被导出排除，也没接进插件系统。
  不要误以为是活代码。
- 本文档描述撰写时的工作树状态，领先于 HEAD：`player_database` 尚未纳入版本跟踪，
  几个核心 / 文档文件已修改。checkout HEAD 看不到 `player_database`。

## 十一、从哪里开始阅读

按这个顺序读：

1. `project.godot` —— 自动加载与窗口配置。
2. `core/kernel.gd` —— 服务装配，60 行。
3. `core/plugin_manager.gd` —— 读加载路径与 `_reload_single`，这是全仓库最值得花时间的文件。
4. `core/plugin.gd` + `core/plugin_context.gd` —— 契约与访问层。
5. `core/services/scene_director.gd` —— 场景注册与切换。
6. 对照读 `mods/control_panel_base` 与 `mods/streaming_arena` —— 一个面板、一个场景，
   正好覆盖两类能力。
7. `mods/_test_pair_*` + `tests/test_integration.gd` —— 在隔离环境里看「纯事件协作」长什么样。
